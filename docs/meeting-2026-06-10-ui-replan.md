# COUNCIL UI 재설계 페르소나 회의 (2026-06-10)

> 운영자 진단: "현재 UI가 엄청 꼬여 있고 불편하다. 그리고 토론이 배치로 생성돼 한 번에 뱉어지는 느낌이다 — 참여자가 바로바로 얘기하는 것처럼 느껴져야 한다."
> 이 회의는 실제 코드(2026-06-10 기준 `app/(main)/session/[id]/page.tsx`, `hooks/useDebate.ts`, `components/debate/*`)를 근거로 진행됐다.

---

## 회의 주제

**"COUNCIL의 토론 화면은 왜 꼬였는가, 그리고 '살아있는 토론'처럼 느껴지려면 무엇을 걷어내고 무엇을 새로 깔아야 하는가?"**

참석 페르소나:

1. **인터랙티브 내러티브 디자이너** (Disco Elysium·Persona 5 류 게임 연출 전문)
2. **UI/UX 정보구조 전문가** (모바일 퍼스트 제품)
3. **LLM 프로덕트 엔지니어** (스트리밍·실시간 AI UX 구현)
4. **비판적 프로덕트 임원** (출시·우선순위 결정권자)

# 1. 현재 상태에 대한 공통 인식

회의 전, 네 명이 코드를 함께 검토하고 다음 사실에 합의했다.

* 트랙 ⑤-1 청크 엔진(1회 호출 = 3~5턴 미니 장면 + 갈림길)은 설계 의도대로 작동한다. 토큰 문제를 푼 것은 사실이다.
* 그러나 지난 한 달간 ⑤-2a(스테이지 스트립), ⑤-5g(스피커 스포트라이트), ⑤-5h(토론 무대), ⑤-5f(사운드), ⑤-5h(배경 선택), ⑤-2b(페르소나 드로어), ③(카드 디렉션), ⑤-1f-B(대기 메모)가 **전부 같은 한 화면에 누적**됐다. 걷어낸 것은 없다.
* 그 결과 세션 화면 한 페이지에:
  * **화자 표시 시스템이 3중**으로 존재한다 — `DebateStage`(전신 컷아웃 무대) + `SpeakerSpotlight`(피드 상단 스포트라이트) + `PersonaStageStrip`(orb 줄). 뒤의 둘은 `DebateFeed` 안에 sticky로 박혀 있어서, 무대 아래 '대화 기록'을 펼치거나 대화록 오버레이를 열면 **무대와 스포트라이트가 동시에 두세 개** 보인다.
  * **`DebateFeed`가 한 페이지에서 3곳**에 렌더된다 — ① 무대 아래 `<details>` 접힘 섹션, ② 풀스크린 대화록 오버레이, ③ 비재생 phase의 본문. 대화록을 보는 길이 2개라서 사용자는 어느 쪽이 '진짜'인지 모른다.
  * **오버레이·시트가 5종** 겹친다 — 대화록 오버레이, BackgroundPicker, PersonaDetailDrawer, SteeringPanel, 하단 sticky DebateControls.
* '배치 느낌'의 근원도 코드로 확인됐다. `lib/ai/client.ts`는 전부 `generateObject` — **청크 전체(3~5턴)가 다 만들어질 때까지 화면은 죽은 대기**이고(WaitingMemoArea로 가림), 도착한 뒤에야 완성된 카드가 `readingTime` 간격으로 하나씩 '뿅' 하고 등장한다. 글자가 흘러나오는 발화가 아니라, 완성문 슬라이드쇼다.
* `docs/spec-debate-playback.md`·`roadmap.md`·`backlog.md` 전체를 검색한 결과 **"stream" 언급 0건** — 스트리밍 발화는 현재 작업계획에 *없다*. (운영자 질문 "향후 작업계획에 이게 있겠지?"에 대한 답: **없었다. 이번 회의로 1순위에 박제한다.**)

> 공통 평가: "⑤-1의 *두뇌*(청크+갈림길)는 옳았다. 문제는 *몸*이다 — 렌더링 레이어가 세대교체 없이 지층처럼 쌓였고, 재생이 '생성 끝난 뒤 틀어주는 녹화방송'이라 라이브처럼 느껴지지 않는다."

# 2. 페르소나별 발의

## A. 인터랙티브 내러티브 디자이너 발의

### 핵심 관점

"연출의 제1원칙은 **시선을 한 곳에 두는 것**이다. 지금 COUNCIL은 무대를 만들어놓고 객석에도 스크린을 달고 복도에도 스크린을 달았다. 관객은 어디를 봐야 할지 모른다."

### 부족한 부분

첫째, **무대가 주인공이 아니다.**
⑤-5h가 만든 `DebateStage`(60vh, 컷아웃, 대사 박스)는 방향이 맞다. Persona 5나 Ace Attorney가 증명했듯 '한 명이 화면을 차지하고 말하는' 연출은 몰입을 만든다. 그런데 바로 아래 `<details>` 대화 기록을 펼치면 그 안의 `DebateFeed`가 자기 무대(`SpeakerSpotlight` + `PersonaStageStrip`)를 또 들고 나온다. 같은 화자가 위 무대에서 한 번, 아래 스포트라이트에서 또 한 번 말한다. **연출이 자기 자신과 경쟁한다.**

둘째, **대사가 '등장'하지 '발화'하지 않는다.**
`DebateStage`의 대사 박스는 `line`을 통째로 꽂는다. 비주얼 노벨에서 대사가 한 글자씩 흐르는 건 장식이 아니라 *그 캐릭터가 지금 말하고 있다*는 신호다. 완성문이 즉시 뜨면 '읽기 자료'고, 글자가 흐르면 '발언'이다. 이 차이가 운영자가 말한 '배치 느낌'의 절반이다.

셋째, **대기 시간이 무대 밖에 있다.**
청크 생성 중 무대는 '준비 중…' 배지 하나 띄우고 멈춰 있고, 그 아래 별도 박스(WaitingMemoArea)가 뜬다. 죽은 시간을 메모로 메우는 건 증상 치료다. 진짜 해법은 죽은 시간 자체를 없애는 것(→ C 발의)이고, 남는 1~2초는 무대 *안에서* 처리해야 한다 — 화자가 숨을 고르고, orb가 웅성거리는.

### 제안

**"무대 단일 시선" 원칙**: 재생 중 화면에는 화자 표시 시스템이 정확히 1개만 존재한다.

* `PersonaStageStrip`은 `DebateStage` **안으로** 흡수 — 무대 상단에 참석자 orb 줄(현재 화자 글로우). 별도 컴포넌트로 피드에 두지 않는다.
* `SpeakerSpotlight`는 **폐기**. 역할이 무대와 100% 중복.
* 대사 박스는 **글자 단위 타이핑 reveal** (스킵 탭 = 즉시 완성, 기존 skipTurn 제스처 유지).
* 대기 연출: 다음 화자 orb 맥동 + "OOO이 반박을 준비합니다" — 무대 안에서.

## B. UI/UX 정보구조 전문가 발의

### 핵심 관점

"화면이 꼬였다고 느끼는 건 미적 문제가 아니라 **같은 정보로 가는 경로가 여러 개**라는 구조 문제다. 경로가 2개면 사용자는 둘 다 의심한다."

### 부족한 부분

첫째, **대화록 진입점이 2개다.**
무대 아래 `<details>` 접힘 섹션과 무대 우상단 버튼의 풀스크린 오버레이. 둘 다 같은 `revealedMessages`를 보여준다. 코드상으로도 `DebateFeed` 3회 렌더 — 유지보수도 인지부하도 2배.

둘째, **phase에 따라 화면 구조가 통째로 바뀐다.**
`stageActive`(generating/playing/steering)면 무대+details, 아니면 피드 단독. 토론이 끝나는 순간 화면 골격이 갈아엎어진다. 사용자 멘탈 모델은 "방이 하나 있고, 토론이 진행된다"인데 실제로는 방이 두 개다.

셋째, **세션 페이지가 신(神) 컴포넌트다.**
`page.tsx`가 useState 6개 + 스토어 2개 + 파생값 5개를 직접 조립한다. headerOpen, soundMuted, selectedMemberId, bgPickerOpen, transcriptOpen… 새 기능마다 여기에 상태가 하나씩 늘었다. 꼬임은 화면에 보이기 전에 이 파일에서 먼저 일어났다.

### 제안

**"방 하나, 층 두 개" 정보구조**:

```text
[세션 화면 = 항상 같은 골격]
┌─────────────────────────┐
│ 헤더 (고민, 접힘)          │
│ ───────────────────────  │
│ 무대 (Stage)              │  ← 항상 존재. 재생 중엔 살아있고,
│   · 참석자 orb 줄 (내장)    │     idle/종료 후엔 단체샷+요약으로 정적.
│   · 화자 + 대사            │
│ ───────────────────────  │
│ 회의록 (Feed)             │  ← 항상 같은 자리, 접고 펴기 1곳.
│ ───────────────────────  │
│ 컨트롤 (sticky)           │
└─────────────────────────┘
```

* 풀스크린 대화록 오버레이 **삭제**, `<details>` 대신 무대 아래 고정 회의록 패널 1곳 (기본 접힘, 재생 끝나면 자동 펼침).
* `DebateFeed`에서 `PersonaStageStrip`·`SpeakerSpotlight` **제거** — 피드는 순수 기록 뷰로 강등. 페르소나 필터(드로어)는 유지.
* 세션 페이지 상태를 `useStageStore`(또는 신규 `useSessionUiStore`)로 이관 — 시트/드로어 열림 상태 단일 관리, 동시에 1개만 열림 보장.
* SteeringPanel·WaitingMemoArea는 무대 하단 슬롯에 **교대로** 들어가는 것으로 위치 고정 — 화면 어딘가에 불쑥 추가되지 않게.

## C. LLM 프로덕트 엔지니어 발의

### 핵심 관점

"'배치로 생성해서 한 번에 뱉는다'는 체감은 정확한 진단이다. 그런데 청크 모델을 버릴 필요가 없다 — **생성과 재생을 직렬에서 병렬로 바꾸면 된다.** 한 호출은 그대로 두고, 그 호출의 *출력을 흘려받으면* 된다."

### 부족한 부분

첫째, **`generateObject`는 전부-아니면-무(無)다.**
현재 `generateChunk`는 3~5턴 + nextTopics가 *전부* 완성될 때까지 아무것도 주지 않는다. 청크가 길수록 죽은 대기가 길어진다 — ⑤-1f-A에서 transcript 압축·maxTokens로 줄였지만, 구조적 한계는 그대로다.

둘째, **재생 엔진이 '도착 완료'를 전제한다.**
`useDebate`의 재생 effect는 `currentChunkTurns`(완성된 배열)를 timer로 한 턴씩 드러낸다. 즉 첫 글자가 보이는 시점 = 마지막 턴 생성 완료 시점 이후. 모델이 첫 턴을 3초 만에 다 썼어도 사용자는 그걸 20초 뒤에 본다.

### 제안

**스트리밍 청크 재생 (가칭 트랙 ⑤-6)** — Vercel AI SDK의 `streamObject` partial object 스트리밍 활용:

```text
현재 (직렬):
generateObject [■■■■■■■■■■ 20s 죽은 대기] → 재생 [턴1][턴2][턴3]…

개선 (병렬):
streamObject [■■■ 턴1 완성 3s] ─▶ 즉시 턴1 타이핑 재생
             [■■■ 턴2 완성    ] ─▶ 버퍼 → 턴1 끝나면 이어 재생
             [    …            ]    (생성이 재생보다 빠르므로 끊김 없음)
```

구현 골자:

* `generateChunk` → `streamChunk`: `streamObject`의 `partialObjectStream`을 순회, `turns[i]`의 `message`가 닫히는 시점(다음 턴 시작 또는 스트림 종료)에 해당 턴을 "재생 가능" 큐에 push.
* `useDebate` 재생 엔진: "완성 배열 timer 재생" → **"큐 소비 재생"**. 큐가 비면 '다음 화자 준비 중' 연출(A 발의), 차 있으면 readingTime 페이싱 유지. 생성 속도 > 읽기 속도이므로 보통 첫 턴 이후 끊기지 않는다.
* 턴 내부는 카드/대사 박스에 글자 단위 reveal — 토큰 스트림을 그대로 흘려도 되고(진짜 라이브), 완성 턴을 타이핑 연출로 흘려도 된다(구현 단순, 페이싱 제어 쉬움). **1차는 후자 권장** — 체감 차이 거의 없고 sanitize(환각 화자 드롭)를 턴 단위로 안전하게 끼울 수 있다.
* 검증·저장은 지금처럼 청크 완성 시점에 일괄(`sanitizeChunk`, `appendMessage`) — 스트림은 *표시용*, 저장은 *완성본*. 데이터 무결성 회귀 0.
* 폴백(`runWithFallback`) 호환: 스트림 중 에러 시 해당 청크를 통째로 다음 공급사로 재시도 — 이미 표시된 턴은 유지하고 이어붙이지 않고, 청크 단위 재생성 (단순함 우선).
* 효과: **체감 대기 20s → 3s 안팎**, WaitingMemoArea는 첫 턴 도착 전까지만 노출되는 보조 기능으로 자연 강등.

리스크: partial JSON 파싱 중 미완성 턴을 성급히 재생하는 것 — "다음 턴이 시작되거나 스트림이 끝나야 직전 턴 확정" 규칙으로 차단. 공급사별 스트리밍 지원 차이는 providers 테이블에 `supportsStream` 플래그로, 미지원 공급사는 현행 generateObject 경로 유지(점진 전환).

## D. 비판적 프로덕트 임원 발의

### 핵심 관점

"한 달 동안 덧셈만 했다. 게임화, 사운드, 배경, 스포트라이트, 무대 — 전부 각각은 좋은 결정이었는데 **아무도 철거를 승인하지 않았다.** 이번 스프린트는 뺄셈이다."

### 날카로운 지적

첫째, **'레이어를 얹는다'는 로드맵 원칙이 부채가 됐다.**
트랙 ③의 "급진적 재설계 ✗ — 레이어를 얹는다"는 당시엔 옳았다. 하지만 ⑤-2 → ⑤-5g → ⑤-5h를 거치며 *대체*가 아니라 *공존*이 됐다. 스포트라이트는 무대가 나온 순간 죽었어야 했다.

둘째, **새 기능보다 회귀가 먼저다.**
백로그의 ⑤-5 게임화 잔여, Phase E 멀티트레이트는 전부 *이 꼬인 화면 위에* 쌓일 예정이었다. 토대가 꼬였는데 증축하면 철거 비용만 커진다. **⑤-5 잔여와 Phase E는 UI 통합이 끝날 때까지 동결한다.**

셋째, **'라이브 체감'은 옵션이 아니라 제품의 본질이다.**
COUNCIL의 약속은 "패널이 내 고민을 *토론해준다*"이다. 녹화방송 체감이면 그 약속이 깨진다. 스트리밍 발화(⑤-6)는 폴리시 항목이 아니라 **차별점 그 자체**다. 로드맵에 없었다는 게 발견된 이상, 최우선으로 박제해야 한다.

넷째, **성공 기준 없이 끝내지 마라.**
이번 재설계의 합격선을 정한다:

| 지표 | 합격선 |
| --- | --- |
| 첫 발언까지 체감 대기 | 5초 이내 (현재 청크 전체 생성 시간) |
| 한 화면의 화자 표시 시스템 | 정확히 1개 |
| 대화록 진입 경로 | 정확히 1개 |
| `DebateFeed` 렌더 위치 | 1곳 |
| 세션 페이지 로컬 useState | 2개 이하 |
| 기능 회귀 (디렉션·메모·갈림길·드로어·결론) | 0건 |

# 3. 회의 중 나온 핵심 쟁점 (실시간 공방)

## 쟁점 1. 무대(Stage)를 살릴 것인가, 피드로 회귀할 것인가

**UI/UX 전문가**: 솔직히 묻자. 꼬임의 진원지는 ⑤-5h 무대다. 무대를 걷어내고 피드+스트립(⑤-2a 시절)으로 돌아가면 구조는 즉시 단순해진다.

**내러티브 디자이너**: 반대다. 무대는 COUNCIL이 ChatGPT 다인 채팅과 갈라지는 지점이다. 걷어낼 건 무대가 아니라 무대의 *경쟁자들*이다 — 스포트라이트, 피드 속 스트립.

**임원**: 데이터 없는 취향 싸움처럼 들리는데. 운영자 피드백 원문이 뭐였나?

**UI/UX 전문가**: "페르소나 구분이 헷갈리고 몰입감이 부족하다"(05-26)였다. 그게 ⑤-2의 출발이었고… 인정한다, 몰입 요구는 운영자한테서 나왔다.

**내러티브 디자이너**: 그리고 "UI가 꼬였다"(오늘)는 무대가 생겨서가 아니라 *셋이 공존해서*다. 하나만 남기면 두 불만이 동시에 풀린다.

**LLM 엔지니어**: 구현 관점 하나만 — 무대는 스트리밍 reveal과 궁합이 제일 좋다. 대사 박스 하나에 글자를 흘리는 게, 피드 카드 여러 장에 흘리는 것보다 시선 집중도 구현도 깔끔하다.

**임원**: 정리한다. **무대 유지, 단일 시선 원칙 채택, 스포트라이트 폐기.** 단, 무대가 싫은 사용자를 위한 '회의록만 보기'는 회의록 패널 펼침으로 자연 제공되는 걸로.

## 쟁점 2. 스트리밍 — 진짜 토큰 스트림인가, 타이핑 연출인가

**내러티브 디자이너**: 글자가 흐르기만 하면 사용자는 구분 못 한다. 타이핑 연출이면 충분하지 않나.

**LLM 엔지니어**: 절반만 맞다. 연출만으로는 **죽은 대기 20초가 그대로다.** 운영자 불만은 둘이다 — '한 번에 뱉는다'(연출 문제)와 '기다린다'(파이프라인 문제). 타이핑 연출은 전자만 푼다. `streamObject`로 턴 단위 조기 재생을 해야 후자가 풀린다.

**내러티브 디자이너**: 그럼 합치자. 파이프라인은 스트리밍, 카드 안 글자는 연출 — 페이싱을 우리가 쥔다.

**LLM 엔지니어**: 그게 정확히 내 제안이다. 토큰을 화면에 직결하면 모델 속도에 연출이 끌려간다. 턴 확정 즉시 큐에 넣고, 재생은 readingTime으로 우리가 지휘한다.

**임원**: 공급사 다 지원되나? Groq·Cerebras 같은 무료 티어가 핵심인데.

**LLM 엔지니어**: OpenAI 호환 스트리밍은 사실상 표준이지만, 공급사별 `supportsStream` 플래그 + generateObject 폴백 경로를 남긴다. 전환은 점진, 회귀는 0.

## 쟁점 3. 지금 백로그(⑤-5 게임화, Phase E)와의 순서

**임원**: 백로그 그대로 가면 ⑤-5e → ⑤-5 → Phase E다. 전부 이 화면 위에 쌓인다. 동결을 제안한다.

**UI/UX 전문가**: 동의하되 예외 하나 — ⑤-5e의 reveal 튜닝(180ms/char, 쿨타임)은 스트리밍 재생 엔진에 그대로 계승되는 자산이다. 버리는 게 아니라 ⑤-6 안으로 흡수.

**내러티브 디자이너**: ⑤-5 게임화도 폐기가 아니라 *연기*다. 시그니처 멘트·사운드는 이미 출하됐고 무대 단일화 후에 더 빛난다.

**임원**: 좋다. **동결이 아니라 '재배치'로 기록한다.** 단, UI 통합(R-1)과 스트리밍(R-2)이 합격선을 넘기 전까지 신규 연출 기능 PR은 내가 막는다.

## 쟁점 4. 한 번에 갈아엎나, 두 스프린트로 나누나

**LLM 엔지니어**: 스트리밍이 급하니 ⑤-6부터 하고 UI 통합을 나중에 하자는 유혹이 있을 거다. 반대다 — 스트리밍 reveal을 *세 군데 화자 표시*에 다 꽂으면 꼬임이 세 배가 된다.

**UI/UX 전문가**: 동의. **순서는 뺄셈 먼저다.** R-1(통합)이 끝나면 reveal을 꽂을 자리가 무대 한 곳으로 줄고, R-2 구현이 절반 난이도가 된다.

**임원**: 채택. R-1은 LLM 호출 코드를 한 줄도 안 건드리는 순수 UI 작업으로 격리 — 회귀 리스크 분리.

# 4. 최종 합의안

## COUNCIL 토론 화면의 원칙 3개

1. **단일 시선** — 재생 중 화자 표시 시스템은 화면에 정확히 1개 (무대).
2. **단일 경로** — 모든 정보(대화록·페르소나·설정)로 가는 길은 1개씩.
3. **생성과 재생의 병렬** — API 호출이 끝나길 기다렸다 트는 녹화방송이 아니라, 만들어지는 즉시 말하기 시작하는 생방송. *"API 호출은 방향 결정에 쓴다"(⑤ 원칙)에 한 줄 추가: "출력은 흘려받는다."*

## 운영자 질문에 대한 답

"참여자가 바로바로 얘기하는 것" = 스트리밍 발화는 **기존 로드맵·스펙·백로그 어디에도 없었다** (전문 검색 "stream" 0건). 이번 회의로 **트랙 ⑤-6**으로 신설하고 R-2에 배치한다.

# 5. 재수립된 작업계획

## Phase R-1 — 뺄셈 스프린트: 무대 단일화 (선행, 순수 UI)

목표: 화자 표시 1개, 대화록 경로 1개, DebateFeed 렌더 1곳.

할 일:

* `SpeakerSpotlight` 폐기, `PersonaStageStrip`을 `DebateStage` 상단으로 흡수
* `DebateFeed`에서 stageHeader(스트립+스포트라이트) 제거 — 순수 기록 뷰로
* 풀스크린 대화록 오버레이 삭제 → 무대 아래 고정 회의록 패널 1곳 (기본 접힘, 토론 종료 시 자동 펼침)
* idle/concluded에도 무대 골격 유지 (정적 단체샷 + 시작/결론 CTA) — phase 간 화면 골격 동일화
* SteeringPanel·WaitingMemoArea를 무대 하단 슬롯에 교대 배치로 위치 고정
* 세션 페이지 useState 6개 → UI 스토어 이관 (시트/드로어 동시 1개 보장)
* 회귀 체크리스트: 디렉션 메뉴 / 대기 메모 / 갈림길 / 페르소나 드로어 / 배경 선택 / 결론 — 6개 기능 무손실

## Phase R-2 — 트랙 ⑤-6: 스트리밍 발화 (신설, 핵심) ★운영자 요구

목표: 첫 발언까지 체감 대기 5초 이내, 발언은 글자 단위로 흘러나옴.

할 일:

* `generateChunk` → `streamChunk` (`streamObject` partialObjectStream, 턴 확정 = 다음 턴 시작 시점)
* `useDebate` 재생 엔진을 "완성 배열 timer" → "턴 큐 소비"로 전환 (readingTime 페이싱·skipTurn·speed·⑤-5e 쿨타임 계승)
* 대사 박스·MessageCard 글자 단위 타이핑 reveal (탭 = 즉시 완성)
* 큐 공백 시 '다음 화자 준비 중' 무대 내 연출 (orb 맥동 + 호명)
* 저장·sanitize는 청크 완성 시 일괄 — 스트림은 표시용, 저장은 완성본 (무결성 회귀 0)
* 공급사 `supportsStream` 플래그 + generateObject 폴백 경로 (점진 전환)
* WaitingMemoArea는 첫 턴 도착 전까지만 노출로 자연 강등

## Phase R-3 — 연출 재개: ⑤-5 잔여 게임화 (동결 해제)

R-1·R-2 합격선 통과 후. 시그니처 멘트·호명 강조·분야 배경이 단일 무대 위에서 재개. ⑤-5e reveal 튜닝 자산은 R-2에 이미 흡수됨.

## Phase R-4 — 트랙 ① Phase E 멀티트레이트 (기존 백로그 복귀)

기존 워크오더(`workorder-persona-E-multitrait.md`) 그대로, 순번만 뒤로.

## 의존 그래프

```text
R-1 무대 단일화 (순수 UI, LLM 코드 불가침)
 └─▶ R-2 ⑤-6 스트리밍 발화 (체감 라이브)
      └─▶ R-3 ⑤-5 게임화 잔여 (동결 해제)
           └─▶ R-4 Phase E 멀티트레이트
```

# 6. 보고서에 넣을 핵심 문장

> COUNCIL의 이번 재설계 방향은 기능을 더하는 것이 아니라, 한 달간 지층처럼 쌓인 세 겹의 렌더링 레이어를 무대 하나로 단일화하고(뺄셈), 청크 생성의 출력을 흘려받아 패널이 *만들어지는 즉시 말하기 시작하는* 생방송 체험으로 전환하는 것(병렬화)이다. 청크+갈림길이라는 두뇌는 옳았다 — 이제 몸을 그 두뇌에 맞춘다.

> 원칙 한 줄 추가: **API 호출은 방향 결정에 쓰고, 출력은 흘려받는다.**
