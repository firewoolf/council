# Gold Standard — 청크 1회 호출이 만들어야 할 산출물

> 트랙 ⑤-1 청크 엔진(`workorder-debate-5-1-chunk-engine.md`)이 *재현* 해야 할 목표 품질.
> 이 토론은 2026-05-26 Opus 가 COUNCIL 의 세 가지 진단(토큰·UI/UX·뻔함)을 의제로 시뮬한 결과 — 실제 LLM 한 호출이 이런 청크를 만들어야 트랙 ⑤가 통과로 본다.
> 작성: Opus (시뮬레이션 + 분석)

---

## 1. 메타 — 왜 이것이 gold standard 인가

분석 포인트 (구현이 재현해야 할 *구조적 특징*):

1. **발언 단위가 문단**, 채팅 한 줄이 아님 → 한 발언 안에 *주장 + 근거 + 함의* 가 다 들어있다.
2. **충돌이 명시적·구조화** — "동의합니다 / 동의하지만 한발 더 / 두 분 다 결과 를 말씀하시는데 저는 메커니즘 을 봅니다" 식 *반박 시그널* 이 발언 첫 줄에 박힌다. 카드 UI 가 이걸 시각화할 수 있다(반박 라인·색대비).
3. **사회자가 능동 진행** — 발언 사이에 *충돌점 정리* + *우선순위 질문* 으로 다음 라운드의 의제를 좁힌다. 단순 "다음 누구?" 가 아니라 *의미 있는 분기* 를 만든다.
4. **자연스러운 nextTopics 분기점** — 사회자의 "CEO 씨, 다음 세 달 안에 사용자에게 보여줄 한 가지를 고른다면?" 같은 질문이 곧 nextTopics 후보가 된다.
5. **결론이 *합의/갈림/질문* 으로 자연 분리** — 마지막 종합에서 세 사람이 *동의한 한 줄* + *각자의 단서 조건* 이 명확히 분리됨. "동의" 와 "단 한 가지" 가 같은 발언에 공존.
6. **굴복 금지가 작동** — 잡스가 사회자 종합에 동의하면서도 "한 가지 — `nextTopics` 의 못 본 각도 가 1개가 아니라 *반드시 1개* 여야 합니다" 로 자기 입장 추가. 페르소나가 *추가 제약을 들고 들어옴*.

## 2. 청크 한 단위로 본 구조

```
[헤더]
  주제: <소주제 한 줄>           ← 청크의 정체성
  참여자: <CastMember[]>

[발언 시퀀스 — 8~12턴]
  사회자 — 의제 박제 (1턴)
  ↓
  3명 진단 발언 (각 1턴)         ← 1라운드
  ↓
  사회자 — 충돌점 정리 + 압박 질문 (1턴)
  ↓
  3명 처방 발언 (각 1턴, 상호 반박)  ← 2라운드
  ↓
  사회자 — 한 줄 종합 + 동의 확인 (1턴)
  ↓
  3명 동의/단서 (각 1턴)         ← 클로징
  ↓
  사회자 — 종결 (1턴)

[nextTopics — 4개]
  ① 주류 의제 (사용자가 떠올렸을 법한)
  ② 반대 각도 (반박의 연장)
  ③ 우선순위/실행 각도 (How 차원)
  ④ *못 본 각도* — 사용자가 떠올리지 못한 트레이드오프 (반드시 1개, Opus 직접 박제 제약)

[결론 단편 — chunk 끝마다 누적되는 raw 단서]
  합의된_것: ["발언 단위가 너무 작다", "채팅 메타포 한계"]
  갈린_것:   ["우선순위 — 청크 우선 vs UI 우선 vs 정체성 우선"]
  당신이_답해야_할_질문: ["다음 분기 한 가지만 고른다면?"]
```

`chunkSchema` 의 형태 — 트랙 ⑤-1 워크오더 §3 의 zod schema 가 이 모양을 강제해야 한다.

## 3. 토론 본문 (Opus 가 만든 reference)

> 의제: COUNCIL 의 세 가지 진단 — 토큰 비용·UI 차별점·뻔함.
> 패널: 🟦 스티브 잡스 / 🟩 스타트업 CEO / 🟪 UI/UX 전문가
> 사회자: ⚪ 100분 토론 사회자

### 1라운드 — 진단

**⚪ 사회자:** 세 의제를 묶어 한 가지 질문으로 시작합니다. "지금 COUNCIL 은 *무엇이 아닙니까?* 그게 분명해져야 무엇이 돼야 하는지 잡힙니다." 잡스 씨부터.

**🟦 잡스:** 단순합니다. **이건 그냥 ChatGPT 의 다인용 버전이에요.** 실시간으로 한 줄씩 발언이 떨어지는 채팅. 사람들이 ChatGPT 를 떠나 *이걸* 켤 이유가 한 줄도 없다. 토큰을 빨리 먹는 게 문제가 아닙니다 — **빨리 먹은 토큰이 사용자에게 안 보이는 가치를 만든다는 게 문제**예요. 채팅 인터페이스가 그 가치를 평탄화합니다. 한 발언이 다른 발언을 *진짜로 부수는* 순간이 시각적으로 없어요. 그러니 다 뻔해 보이는 거예요.

**🟩 CEO:** 잡스 씨 의견은 비전 차원에선 맞지만 저는 숫자부터 봅니다. BYOK 라 회사 비용은 0 이지만, **사용자가 자기 키 한도를 한 세션에 다 쓰면 다음 세션에 안 돌아옵니다.** Gemini Flash 무료 키 일일 한도, Groq RPM 한도 — 30분 회의 한 번에 다 태우면 끝. 토큰 절약은 비용 문제가 아니라 **재방문 문제**예요. 그리고 ChatGPT 와 차별화 안 되면 신규 획득 비용이 영원히 안 떨어집니다. 디자인은 그 다음 얘기죠.

**🟪 UI/UX:** 두 분 다 *결과* 를 말씀하시는데 저는 *메커니즘* 을 봅니다. **인지부하가 정렬돼있지 않습니다.** 채팅 카드가 떨어지는 속도가 사람의 읽기 속도보다 빠르고, 누가 누구를 반박하는지 시각적 연결이 약합니다(현재 `replyTo` 라인이 텍스트 한 줄). 사용자가 *충돌* 을 못 보면 *결정* 을 못 합니다. 그리고 발언이 뻔한 이유의 절반은 *발언 단위가 너무 작다* 는 것입니다 — LLM 이 한 턴에 한 발화만 만들면 *반박이 진짜가 되기 전에* 다음 호출로 넘어가요. 한 호출에서 3~5턴짜리 *장면* 을 만들어야 반박이 살아납니다.

**⚪ 사회자:** UI/UX 전문가 발언이 흥미롭네요. *기술적 비용 절감* 과 *발언 품질* 이 같은 해결책 — *발언 단위를 키운다* — 으로 묶이는군요. CEO 와 잡스 씨, 이건 동의합니까?

**🟩 CEO:** 동의합니다. **하나의 호출로 여러 턴** 이면 토큰당 가치가 올라가고 한도 소진이 늦어집니다. 다만 *생성된 청크를 사용자가 어떻게 조향하느냐* 가 핵심 — 사용자가 "다음에 뭘 다룰지" 못 정하면 결국 ChatGPT 입니다.

**🟦 잡스:** 동의하지만 한발 더 갑니다. **사용자의 역할이 "감독" 으로 바뀌어야 해요.** 채팅을 보는 게 아니라 *연출* 을 보고 *다음 장면을 고르는* 사람이 돼야 합니다. ChatGPT 와의 차이가 거기에 있어요 — *결정* 을 위한 도구지 *답변* 을 받는 도구가 아니다.

### 사회자 정리 — 첫 충돌점

**⚪ 사회자:** 잠깐 짚어둡니다. 세 분이 *현상* 에 대해선 동의 — "발언 단위가 너무 작고 채팅 메타포가 한계다." *처방* 으로 갈수록 갈립니다:

- 잡스: **채팅 메타포 폐기**. "감독이 장면을 고르는" 모드로.
- CEO: **호출당 가치 극대화**. 다턴 청크 + 조향 분기.
- UI/UX: **충돌 가시화**. 반박 시각화·정보위계 재설계.

세 처방이 *호환됩니다*. 그런데 *우선순위* 가 다릅니다. CEO 씨, 다음 세 달 안에 사용자에게 보여줄 한 가지를 고른다면?

### 2라운드 — 처방·우선순위

**🟩 CEO:** **청크 엔진 먼저.** 이유는 두 가지. 첫째, 토큰 한도 문제가 가장 시급한 *이탈 트리거*예요. 둘째, 청크가 깔리면 **시각화도 청크 단위로 설계**할 수 있어 UI 작업이 깔끔해집니다 — 발언 하나씩 떨어지는 걸 시각화하려면 모션 타이밍 지옥이지만, 청크 = 한 *장면* 으로 묶이면 그 안의 반박을 굳이 실시간으로 시뮬할 필요가 없어요.

**🟪 UI/UX:** 동의합니다. 다만 청크 엔진을 짜면서 *재생 레이어* 를 같이 설계해야 합니다. 청크가 백엔드에서 한 번에 생성돼도 사용자 화면엔 **읽기 속도에 맞춰 점진적으로 드러나야** 해요 — 한꺼번에 5턴이 떨어지면 그것도 인지부하 폭탄입니다. *재생 정책* 자체가 UI의 일부.

**🟦 잡스:** 그건 *어떻게* 의 문제고, 저는 *왜* 를 한 번 더 짚겠습니다. **청크 끝마다 사용자가 다음 소주제를 고르는 그 순간** — 그게 COUNCIL 의 정체성이에요. ChatGPT 는 사용자가 다음 메시지를 *입력* 하지만, COUNCIL 은 사용자가 다음 *방향* 을 *선택* 합니다. 입력 → 선택. 이 한 단계의 차이가 도구의 성격을 바꿔요. 그래서 *`nextTopics` 의 품질이 제품의 성패* 입니다. 4지선다가 뻔하면 다 죽어요.

**⚪ 사회자:** 잡스 씨, "뻔함" 의 정의를 한 줄로 잡읍시다. 사용자가 *생각도 못 한 각도* 가 후보에 떠야 한다는 거죠?

**🟦 잡스:** 정확히. **사용자가 보지 못한 트레이드오프** 가 후보로 떠야 합니다. "사용자가 이걸 묻고 싶었지만 묻지 못한 것" — 이게 인사이트의 정의예요.

**🟪 UI/UX:** 그 *못 본 각도* 를 어떻게 시각적으로 차별화할지도 함께 설계해야 합니다. 4개 후보를 같은 톤의 칩으로 나열하면 결국 다 비슷해 보여요. *"합의된 것 / 끝내 갈린 것 / 당신이 답해야 할 질문"* — 이런 비대칭 정보위계가 후보 자체에 들어가야 합니다.

**🟩 CEO:** 저는 한 가지 더 추가합니다. **세션 사이에 누적되는 무언가** 가 있어야 리텐션이 나옵니다. 지금은 한 세션 끝나면 결론 카드 하나 받고 끝. 사용자가 *두 번째 세션* 에 돌아올 이유가 없어요. 거울 페르소나(트랙 ④) — 사용자 자신의 패턴을 누적해서 다음 세션에 보여주는 — 이건 잡스 씨의 "결정 도구" 정체성에 직결됩니다.

### 사회자 종합 — 한 줄로 정리

**⚪ 사회자:** 정리합니다. 세 분의 처방이 *한 줄로* 묶입니다:

> **COUNCIL 의 다음 마일스톤은 "토론 단위를 청크로 격상 + 청크 끝마다 사용자가 다음 방향을 선택 + 이 선택이 누적돼 사용자의 결정 프로필이 된다."**

세 의제에 매핑하면:
- **토큰 빨리 먹는다 →** 청크 (호출 1회 = 3~5턴, 비용 1/3~1/4)
- **UI/UX 차별점 부재 →** 청크 *재생* + *선택 모먼트* 의 시각적 비대칭
- **뻔하다 →** `nextTopics` 가 *사용자가 못 본 각도* 를 항상 1개 포함

세 분 동의하십니까?

**🟦 잡스:** 동의. 단 한 가지 — `nextTopics` 의 *못 본 각도* 가 1개가 아니라 *반드시 1개* 여야 합니다. 0개면 ChatGPT. 2개 이상이면 사용자가 길을 잃어요.

**🟩 CEO:** 동의. 우선순위는 청크 → 누적 프로필 → 거울 페르소나 순. 한 분기씩.

**🟪 UI/UX:** 동의. 청크 *재생 정책* 과 *선택 모먼트 UI* 는 청크 엔진 워크오더와 같은 PR 에 묶어야 합니다 — 분리하면 백엔드만 바뀌고 사용자는 못 봅니다.

**⚪ 사회자:** 좋습니다. 이 토론은 여기서 종결합니다.

## 4. 이 토론에서 도출된 nextTopics 예시

청크 종료 직후 화면에 떠야 할 4개 분기:

```
① "청크 엔진을 어떻게 설계할까"             ← 주류 — 다음에 자연스러운 질문
② "UI 를 먼저 손보면 안 되나"                ← 반대 각도
③ "한 분기에 청크와 거울 페르소나 둘 다 가능?"  ← 실행/우선순위 (CEO 발언의 연장)
④ "✦ ChatGPT 와 차별화 안 되면 BYOK 자체가 의미 없는 것 아닌가" ← *못 본 각도* (CEO·잡스의 발언이 함의했지만 명시 안 한 결론)
```

✦ 마커는 *못 본 각도* 시각 차별화 (다른 색·다른 위계). 사용자가 ✦ 를 클릭하면 트랙이 한 단계 깊어진다.

## 5. 구현 함의 (트랙 ⑤-1 워크오더에 박제)

이 산출물을 LLM 한 호출로 만들려면 다음 제약을 `buildChunkPrompt` 가 강제해야 한다:

| 제약 | 표현 |
|---|---|
| 발언 단위 = 문단 (3~5문장) | "한 발언은 한 줄이 아닌 한 문단. 주장·근거·함의가 다 담길 것." |
| 충돌 명시 | "발언 시작에 *동의/반박/조건부 동의* 시그널을 박제. '동의합니다만…' '두 분 다 결과를 보는데…' 식." |
| 사회자 능동 진행 | "사회자는 단순 다음 화자 호출이 아니라 *충돌점 정리 + 압박 질문* 으로 다음 라운드의 의제를 좁힌다." |
| `nextTopics` 못 본 각도 | "후보 4개 중 1개는 반드시 *사용자가 떠올리지 못한 트레이드오프*. 사용자 발언·질문에서 *함의되었지만 명시되지 않은* 결론을 추출." |
| 굴복 금지 유지 | "BASE_PROMPT 의 굴복 금지가 청크 안에서도 작동. 페르소나가 사회자 종합에 동의해도 *자기 단서 조건을 추가* 할 수 있다." |
| 결론 *합의/갈림/질문* 분리 | "청크 종료 시 chunkResult.consensus / divided / openQuestion 세 필드 분리. 한 통의 4섹션 결론이 아니다." |

→ 이 표는 워크오더 `workorder-debate-5-1-chunk-engine.md` 에 직접 박제될 예정.
